## 交给 Gemini 前的注意事项

Gemini 上次主要问题不是想法不够，而是没有先核对当前代码事实，导致文档和实现状态脱节。继续交给 Gemini 做时，必须先遵守下面这些约束：

- 先读源码再判断，不要根据旧文档或印象写结论。比如 2048 已经有 `use2048Engine`，贪吃蛇已经有粒子、震动和虚拟手柄，俄罗斯方块已经有 Hold、ghost、技能和 3D 渲染。
- 不要把已经完成的能力写成待办。写文档前至少看对应页面、样式、`src/lib` 或 hooks。
- 不要只写“重制”“升级”“加入对象池/四叉树/ECS”这类大词。每条建议必须能落到当前代码里的具体文件和下一步动作。
- 优先做 P0，不要一上来做 Boss、复杂道具、完整美术管线、复杂音频系统这类扩展。
- 保持 KISS。小游戏先修可玩性、一致性、移动端、统计和规则测试，不要过度设计。
- 改代码时不要破坏现有测试锚点。页面测试依赖中文标题、按钮、分数、步数等文本，改 UI 文案要同步改测试。
- 中文站点优先中文文案。避免留下 `Score`、`Best`、`Game Over`、`Too High` 这类英文混杂。
- 移动端必须实际考虑输入方式。Canvas 游戏不能只支持键盘或鼠标，至少要确认虚拟手柄、pointer 或触屏手势之一能玩。
- Canvas/3D 游戏不能只看 DOM。涉及画布尺寸、遮挡、手柄可见性时，要用浏览器实际打开桌面和 390px 左右移动视口看一遍。
- 规则 bug 要优先抽纯函数和补测试。不要只在组件里直接改一坨状态，尤其是贪吃蛇、打砖块、飞机、坦克这类循环游戏。
- 随机逻辑如果要测试，优先支持可注入 RNG。不要让测试依赖真实 `Math.random`。
- 接入统计时优先用现有 `useGameStore`，不要再单独散落新的 `localStorage` key，除非当前游戏已有明确历史兼容需求。
- 改虚拟手柄时复用 `VirtualController`，不要每个游戏再写一套方向键。
- 每次只做一个小游戏或一组强相关 P0。不要一次性大改全部游戏代码，否则回归成本太高。
- 做完必须跑验证：至少 `pnpm run typecheck` 和相关 `rstest`；如果改了共享组件或多个游戏，再跑 `pnpm run test`。
- 如果只是更新优化文档，不能把文档当成事实来源；文档必须反映当前代码，而不是反过来用文档幻想当前状态。
